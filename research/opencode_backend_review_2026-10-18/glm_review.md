# Independent read-only review — Telos 50M COROSred TPU/CUDA quality discrepancy

## 1. What I inspected, and the strongest NEW finding

I read all seven bounded research reports, then verified against originals: `telos/training/trainer_pytorch.py`, `telos/training/xla_utils.py`, `telos/training/lr_schedule.py`, `telos/training/schedule.py` (`get_weights`, `DynamicMetricTracker`), `telos/diffusion/corosred_unified.py` (current + `git show` of revisions), `telos/training/monitor.py`, `telos/train/cli.py`, the full September commit history of the trainer/loss/schedule/diffusion files, and the saved measurement JSONs (`logs/saved_50m_gradient_comparison_20261018.json`, `scratch/backend_parity/hf_50m_file_history.json`). The embedded per-checkpoint configs in the saved JSON proved exceptionally informative and were under-exploited by earlier reports.

**Strongest new finding: the eligible CUDA and TPU runs were not trained on the same loss implementation — and the specific revision boundary is datable.**

- The CUDA-era loss (state at `57f867a`, the 11 September launch recorded in the recovered history) pools as `(α·mean_causal + β·mean_infill)/(α+β)` — `git show 83d9f9c`, i.e. per-task token means with equal 1.0 intra-pool weights.
- Commit `6115532` (14 Sept 15:32) rewrote the pool to `(α·w_c·causal_seq_norm + β·w_m·infill_seq_norm)/(α·w_c+β·w_m)` with `w_c=B_c/B≈0.646`, `w_m=B_m/B≈0.354` ("sequence-normalized loss pooling … to eliminate token count gradient surge").
- CUDA Lightning's final checkpoint was uploaded 2026-09-14 at **15:18 UTC = 20:48 IST** (`hf_50m_file_history.json`), i.e. only ~5¼ h after that commit. A 12,716-step run at any plausible ≥1 step/s finishes in ≤3.5 h, so essentially the entire CUDA Lightning run executed on the **pre-`6115532`** pool. The eligible TPU runs demonstrably postdate `a2f09a0`/`91f7500` (17 Sept — their embedded configs contain `sched_cadence: 1`, a key that did not exist before 17 Sept in that form), so they ran on the **post-`6115532`** pool, before the 22 Sept rework (`ebc7cae`).

Arithmetic (using the runs' actual `causal_ratio=0.65`, incl. the hold→decay α/β sweep): under the TPU-era formula the infill task's relative weight is **0.64× (hold phase), 0.72× (decay phase)** of the CUDA-era weighting, and the gross loss/gradient scale is **≈0.78–0.86×** (for masked-mean ≈ causal-mean ratios of 5–9, per report ~9:1 counts). Direction: predicts a **worse infill** endpoint for the TPU-era runs — consistent with infill CE 1.786/1.712 vs 1.086, and the infill deficit is the larger component of the gap. It does not by itself predict the causal-CE deficit (2.07/2.04 vs 1.56), and Adam absorbs most of a global ~0.8× scale — so this is a bound, not a full cause. But it destroys the premise that both endpoint measurements sit on a single historical objective. Every prior report treats the "matching unified objective" of the two runs as established; the repo's own commit calendar says otherwise.

## 2. Ranked candidate mechanisms

**Candidate 1 — Cross-backend objective-revision mismatch (strongest, NEW).**
Evidence: `git show 83d9f9c` vs `git show 6115532` (file `telos/diffusion/corosred_unified.py`, pool block); CUDA run end bounded by upload 20:48 IST 14 Sept with commit landed 15:32 IST; TPU eligibility keys absent from CUDA config, present in TPU configs. Confirmed code behavior: yes, for both eras (both oldState and newState inspected in git). Historical exercise: high confidence for the TPU side (config fingerprint), bounded-inference for CUDA side. Predicted direction/magnitude: infill gradient relative weight −28% to −36%, overall scale −14% to −22% on TPU-era runs; interacts with the absolute `grad_clip=1.0` (smaller nominal gradients clip less often). Counterevidence: causal-CE deficit is opposite to the predicted causal-emphasis increase; magnitude plausibly sub-nat. Missing: a run start timestamp for CUDA Lightning (from recovered CLI logs) to close the upload inference completely.

**Candidate 2 — TPU runs discard AdamW moments on any resume; CUDA runs restore them.**
Confirmed code behavior: TPU checkpoints never contain optimizer state (`trainer_pytorch.py:422–430`, explicitly "without saving optimizer state"; corroborated by "historical moments are absent from the selected TPU intermediates"), and `cli.py:360–368` restores optimizer state **only** when `device != "xla"` and not TPU — the TPU branch just prints "Optimizer moments initialized natively". CUDA checkpoints do carry full optimizer state (`trainer_pytorch.py:449–455`), so CUDA resumes restore `exp_avg`/`exp_avg_sq`; any TPU resume resets moments to zero at whatever LR the schedule is at, causing over-sized post-resume spins (bias-corrected sign-like steps at late-stage LR that leave the basin).
Predicted direction: per-resume transient, plausibly persistent via repeated Kaggle session restarts — reproducing a structurally TPU-only failure mode with no relationship to BF16 kernels. Counterevidence: whether the cadence-1 TPU lineage actually resumed before its step-4000 intermediate is unestablished (the chain 8000→12000→12716 shows at least one resume during the lineage, but its phase is unknown); a single fresh-moments restart does not obviously produce a −0.5-nat plateau. Missing: resume events with timestamps (session logs) or checkpoint file mtimes.

**Candidate 3 — Metric cadence remained 25 on TPU in the "cadence-1" runs, without decay compensation.**
Confirmed code behavior: at `a2f09a0` the defaults are `25 if is_tpu else 1` for LR/schedule/metric cadence; both eligible TPU embedded configs contain **no** `cadence` or `default_cadence` key (verified in the saved JSON), so metric cadence was still 25 while `sched_cadence=1`. The cadence-scaled EMA decay fix (`3c1331b`, 22 Sept) postdates the runs, so the tracker updated ~500 times with per-call decay instead of ~12,716 times. Effect: gamma/mask_blend gating lags the CUDA run by very large wall-step factors; the γ lever only touches a detached head (`h.detach()`) plus indirect global clipping, so predicted magnitude is small. Note this candidate is a *strengthening*, not a cause: see §3.

## 5. Verdict

**The root cause is not established.** What is established: both eligible runs match on nominal steps/LR/effective batch/architecture, but they (a) demonstrably trained on **different historical loss-pooling revisions** (new, bounded magnitude, direction favoring an infill-deficit contribution), and (b) had **backend-entangled optimizer-resume semantics** (confirmed code, historically unexercised in proven detail), with (c) a lingering metric-cadence confound that no eligible run actually eliminated. None of these is quantitatively sufficient to explain a ~0.5-nat two-task deficit, and the precision/lowering hypothesis remains unevaluated because no accelerator trace exists. The honest statement: a concrete sub-cause (objective mismatch) is now evidenced, the remaining gap is indistinguishable from a pure runtime/kernel effect on current local evidence, and any hardware run should instrument the first post-resume step boundary, not just endpoints.
