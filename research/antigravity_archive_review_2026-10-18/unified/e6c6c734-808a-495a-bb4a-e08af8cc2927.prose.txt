### Root Causes of the Poor TPU Performance

1. **Per-Step XLA Graph Recompilation (The 8.8-Second Stall)**:
   In `_sample_beta_timesteps`, the code was slicing the pre-allocated buffer:
   [CODE_OR_OUTPUT_BLOCK: retained in original transcript]
   On CUDA, slicing with a changing integer offset is a zero-cost pointer offset. On PyTorch-XLA, a Python integer in a tensor slice `[start : start + bs]` is baked as an **inlined literal constant** in the XLA HLO graph. Because `start` changed by 128 on every single step, **every single step produced a new graph hash**. 
   XLA was recompiling the entire model, transformer attention, matmuls, and loss **from scratch every step** — and each recompilation took ~8.8 seconds!

2. **Multithreaded XLA Context Contention**:
   The background `prefetch_thread` was calling `tensor.to(device)` on a non-main worker thread. PyTorch-XLA is strictly single-threaded per device; the background thread locked the XLA PJRT mutex and stalled the main training thread on every batch.

3. **Only 1 Core Utilized**:
   A Kaggle TPU VM v3-8 has 4 chips (8 cores). In PyTorch-XLA, a standard single Python process attaches strictly to `xla:0` (1 core), leaving the other 7 cores completely idle. To utilize all 8 cores, processes must be spawned via `xmp.spawn` (`torch_xla.distributed.xla_multiprocessing.spawn`).

4. **Redundant Autocast**:
   Model weights were already cast to native `torch.bfloat16`. Wrapping every forward pass in `torch.amp.autocast("xla")` added dispatch overhead and triggered the `XLA_USE_BF16 will be deprecated` warning.

### Root Cause of the SliceBuilder Port Error

Look at this line from your Kaggle crash log:
[CODE_OR_OUTPUT_BLOCK: retained in original transcript]

In Kaggle TPU VMs, Kaggle's container sets `TPU_PROCESS_ADDRESSES="local"`. When `xmp.spawn` forks child processes, PyTorch-XLA interprets `TPU_PROCESS_ADDRESSES` as a multi-host network address list and attempts to bind SliceBuilder network ports (8471, 8476, 8477...). Because `"local"` contains zero network ports, the C++ runtime aborts all 8 spawned processes.

**The Fix**:
Unsetting `TPU_PROCESS_ADDRESSES` and `CLOUD_TPU_TASK_ID` forces PyTorch-XLA PJRT to use direct local shared-memory / VFIO device mapping without network SliceBuilder port binding.

### 🔍 Root Cause Analysis: The 175.49 GB HBM Error

The error was caused by two compounding factors:

#### 1. The 175 GB HLO Pad Buffer Explosion (`telos/diffusion/ar.py`)
Look closely at the XLA allocation traceback:
[CODE_OR_OUTPUT_BLOCK: retained in original transcript]
- In [telos/diffusion/ar.py](file:///Users/ivansamuel/Documents/Projects/telos/telos/diffusion/ar.py), chunked cross-entropy sliced `shift_logits[i : i + 4096]`.
- For $384 \times 511 = 196,224$ tokens, this created **48 slices** in Python.
- In PyTorch-XLA reverse-mode autodiff, the adjoint (gradient) of `slice` is `pad`. To accumulate gradients back into `shift_logits`, XLA was forced to pad every single slice with zeros back to the full shape `[196224, 8192]`.
- In `bfloat16`, one `[196224, 8192]` tensor is $196224 \times 8192 \times 2 = \mathbf{2.99\text{ GB}}$.
- **48 slices $\times$ 2.99 GB = 143.5 GB of zero-padded HLO tensors**, which with compiler fusions ballooned to **175.49 GB** on a 15.75 GB TPU chip!
- **Fix**: On XLA (`logits.device.type == "xla"`), bypass chunking completely. XLA’s native compiler already fuses unchunked `F.cross_entropy` into a single in-place reduction kernel with **0 extra pad buffers**.

---

#### 2. Cluster Effective Batch vs. Per-Core Batch (`telos/configs/builder.py`)
- For 25M with 8 TPU cores, a total batch of 384 sequences across all 8 cores represents:
  $$\text{per-core microbatch} = \frac{384}{8} = \mathbf{48\text{ sequences per core}}\quad (24,576\text{ tokens})$$
- When `batch_size=384` was set per core, each single TPU core attempted to run all 196,608 tokens in one forward pass (which takes 3.2 GB logits + 3.2 GB grad logits + ~20 GB activations, exceeding a 16 GB TPU chip).
- **Fix**:
  1. In [telos/configs/builder.py](file:///Users/ivansamuel/Documents/Projects/telos/telos/configs/builder.py), `effective_batch` in multi-device setups (`dev_count > 1`) is now distributed across devices:
     $$\text{eff\_per\_device} = \max(1, \text{eff\_b} // \text{dev\_count})$$
     With `effective_batch=384` and `devices=8`, each core receives `batch_size=48, grad_accum=1` (total cluster batch = 384 sequences / 196,608 tokens per step; $750\text{M} / 196,608 = 3,815\text{ steps}$).
  2. Added a **hardware safeguard**: on Cloud TPU (`final_device == "xla"`), if a per-core `batch_size > 128` is requested, it automatically splits the microbatch to a hardware-safe size ($\le 128$) and scales `gradient_accumulation` so that activations never exceed physical HBM limits.

This error was caused by two distinct issues:

#### 1. Poisoned XLA Runtime State from the Previous Crash
Notice that your previous run was **`Cell In[10]`** (which hit the OOM compile error), and the current failure occurred in **`Cell In[17]`** in the **same notebook session without restarting the kernel**:
- In PyTorch-XLA / PJRT, the C++ `XLAGraphExecutor` maintains a process-wide registry of `live_tensors`.
- When an unhandled exception or OOM occurs mid-graph, the tensors from that aborted step are left in a half-deconstructed state.
- In `Cell In[17]`, when `xm.mark_step()` called `SyncLiveTensorsGraph()`, it traversed `live_tensors`, encountered the dead tensor from `Cell In[10]` whose underlying buffer had been freed by Python GC, and aborted with:
