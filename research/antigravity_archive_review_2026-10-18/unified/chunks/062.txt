### Root Cause 1: The OpenMP 384-Thread Spinlock Storm (Explaining the 4203% CPU)
* **The Mechanism**: A Kaggle TPU v5e-8 VM has **48 vCPU cores**. When Python launched without explicit shell environment caps, GNU `libgomp` (OpenMP) detected 48 cores and set its thread pool to **48 threads per process**.
* When `xmp.spawn` spawned 8 worker processes, each worker inherited a 48-thread pool:
  $$\text{Total active threads} = 8 \text{ processes} \times 48 \text{ threads} = \mathbf{384 \text{ competing threads}}$$
* In Linux GNU `libgomp`, the default idle behavior is **`OMP_WAIT_POLICY=ACTIVE`** (active spinlock). Idle OpenMP threads do not sleep; they burn 100% CPU in tight spin-wait loops waiting for work. 
* Exactly $42$ out of 48 CPU cores were pinned at 100% utilization ($42 \times 100\% = \mathbf{4203.00\% \text{ CPU}}$).

---

### Root Cause 2: glibc Multi-Arena Heap Fragmentation (Explaining the 323.4 GiB RAM Balloon)
* In GNU libc (`glibc`), the memory allocator creates separate heap memory pools ("arenas") to avoid thread lock contention.
* By default, glibc allocates up to **$8 \times \text{number of cores}$** arenas per process:
  $$8 \times 48 = 384 \text{ arenas per worker} \times 8 \text{ workers} = \mathbf{3,072 \text{ independent glibc memory arenas!}}$$
* Each arena maps virtual memory in 64 MiB increments (`mmap`).
* Under the continuous 384-thread spinlock storm, every per-step Python allocation (`batch = np.ascontiguousarray(...).copy()`, `torch.from_numpy(...)`, PJRT host DMA buffers) hit different arenas.
* Crucially: **glibc almost never releases allocated heap memory back to the Linux OS kernel** without an explicit `malloc_trim(0)` call or `MALLOC_ARENA_MAX=2`. The Resident Set Size (RSS) grew monotonically by ~55 MB/step across the cluster, reaching **323.4 GiB**.
