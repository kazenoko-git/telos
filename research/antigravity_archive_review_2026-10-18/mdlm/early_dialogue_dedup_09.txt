You are right. I focused too much on graph execution and algorithmic FLOP removal, and not enough on the actual limiting resource on Apple Silicon: **unified-memory bandwidth**.

For a 25M-model MLX trainer, especially with small physical microbatches and heavy accumulation, much of the backward path can be **memory-bandwidth-bound rather than compute-bound**. In that regime, reducing FLOPs alone is not sufficient; the winning changes reduce reads/writes of activations, gradients, optimizer state, and temporary tensors.

## The useful mental model

For each operation, ask:

\[
\text{Arithmetic intensity} =
\frac{\text{FLOPs}}{\text{bytes read + bytes written}}
\]

- Large BF16 GEMMs—MLP projections and QKV projections—have high arithmetic intensity and may be compute-bound when batch/sequence dimensions are large enough.
- RMSNorm, SiLU, residual adds, masking, CE reductions, gradient additions, and AdamW are low-arithmetic-intensity operations. They read/write lots of memory for relatively little arithmetic, so they are often bandwidth-bound.
- Your gradient accumulation implementation repeatedly reads and writes **every parameter gradient**. That is probably the biggest bandwidth-specific issue in the trainer.

# The main bandwidth bottleneck: gradient accumulation

This line is expensive:

```python
accum_grads = tree_map(lambda a, b: a + b, accum_grads, grads)
```

For every microbatch after the first, it performs roughly:

```text
read existing accumulated gradients
+ read new gradients
+ write updated accumulated gradients
```

For BF16 gradients, a 25M-parameter model means, at a bare minimum:

```text
25M params × 2 bytes = 50 MB per gradient tree
```

Each accumulation add streams approximately:

```text
50 MB read (accumulator)
+ 50 MB read (new gradients)
+ 50 MB write (updated accumulator)
= ~150 MB
```

That excludes allocator effects, MLX graph metadata, potential FP32 gradient/state representations, and the memory traffic required to create `grads` in the first place.

At `gradient_accumulation = 64`, you are potentially adding **many gigabytes of pure gradient-buffer traffic per optimizer step**, before counting the backward pass itself.

This is why a small physical batch with very high accumulation can give poor tokens/sec even when the effective batch is large: effective batch improves optimization semantics, but it does not improve the arithmetic intensity of each microbatch.

If you can safely increase:

```text
physical batch = bs
```

and reduce:

```text
gradient_accumulation
```

while keeping:

```text
bs × gradient_accumulation = fixed effective batch
```

you reduce the number of full gradient-tree accumulation passes.

The evaluation itself is needed if otherwise the lazy graph retains all microbatch activations. But it means each microbatch flushes a full gradient accumulation pass to unified memory.

| Approach | Memory use | Bandwidth / graph cost |

| Delay evaluation through all accumulation | Potentially huge | Larger fused graph, but can retain all graphs/activations |
| Increase physical batch and reduce accumulation | Higher activation memory | **Much lower full-gradient accumulation traffic** |

# Second bandwidth bottleneck: output logits and full-vocabulary CE

For BF16 logits:

\]

```text

BF16 = 2 bytes
```

the logits tensor alone is:

```text

```

That is only the forward logits result—not the associated backward intermediates, reads, softmax/CE activity, or gradient buffers.

and throws away unmasked positions afterwards:

So, even where the LM-head GEMM has enough compute to be efficient, the massive logits materialization and CE path may be consuming a large amount of unified-memory bandwidth.

## Bandwidth-oriented answer: masked-only output head

Split the model before the vocabulary projection:

```python
def hidden_states(self, x):
    x = self.emb(x)
    for layer in self.layers:
        x = layer(x)
    return self.norm(x)
```

Then project only hidden states corresponding to masked positions.

If approximately 50% of eligible tokens are masked, this can roughly halve:

- LM-head input/output traffic,
- logits materialization,
- CE forward traffic,
- CE backward traffic,
- LM-head gradient work.

This is likely your strongest model-specific bandwidth optimization.

### But use a fixed-shape packing strategy

A naïve boolean gather makes the count of selected positions variable. Variable shapes can cause compile-cache misses or recompilation in MLX; compilation is shape-dependent by default. [cite:f401b091-1]

For throughput, prefer a static-capacity pack:

```text
hidden:       [B, T, D]
packed:       [K, D]
logits:       [K, V]
valid_mask:   [K]
```

where `K` is fixed for a run. You may waste some slots, but you preserve compilation and avoid the worst full `[B, T, V]` allocation.

This is an engineering tradeoff:

- exact variable masked gather = minimum FLOPs and bytes, potentially unstable compile behavior;
- fixed packed capacity = slightly more compute, much more predictable execution;
- full logits = simplest, highest bandwidth use.

Benchmark all three.

# Third bandwidth bottleneck: SwiGLU is memory-intensive

Current MLP:

```python
return self.w3(nn.silu(self.w1(x)) * self.w2(x))
```

It creates several full `[B, T, hidden]` intermediates:

```text
w1(x)        [B, T, H]

w2(x)        [B, T, H]
product      [B, T, H]
```

Even if MLX fuses some elementwise components after compilation, backward still needs to access or recompute information for the gate and value paths.

For your MLP expansion:


the MLP activation traffic can exceed attention activation traffic, particularly at shorter sequence lengths.

## What to do

### A. Compile before judging it

`mx.compile` can merge common work and fuse certain operations, reducing intermediate materialization. [cite:f401b091-1]

Your existing compiled `microbatch_step` is the prerequisite. Profile it versus the uncompiled version before changing the MLP architecture.

### B. Fuse gate/up projections

Instead of two separate projections:

```python
self.w1 = nn.Linear(d_model, hidden, bias=False)
self.w2 = nn.Linear(d_model, hidden, bias=False)
```

use one:

```python
self.gate_up = nn.Linear(d_model, 2 * hidden, bias=False)
self.down = nn.Linear(hidden, d_model, bias=False)
```

Then split the result:

```python
gate, up = mx.split(self.gate_up(x), 2, axis=-1)
return self.down(nn.silu(gate) * up)
```

This does not reduce the fundamental output activation size, but can:

- reduce separate input reads of `x`,
- reduce kernel dispatches,
- improve GEMM utilization,
- improve the compiler’s chance of fusing adjacent operations.

Whether it wins on your exact Metal hardware depends on dimensions; benchmark it. For a small model, launch/memory overhead can matter more than raw FLOPs.

Each transformer layer contains roughly:

Every one of these is a read/write pass over `[B, T, D]`.

was important. MLX documents `mx.fast` operations as optimized implementations for common deep-learning operations, including RMSNorm and SDPA. [cite:e5743145-2] Manual RMSNorm would otherwise make several separate memory passes: square, reduction, rsqrt, broadcast multiply, scale multiply.

- keep residuals BF16;
- avoid accidental FP32 promotions;
- compile the layer/microbatch graph;
- use fused normalization;
- avoid adding debug stats, casts, or `.astype()` operations inside blocks.

Your current constants such as:

are good because they are Python scalars.


Interpretation:

If `t_accum` becomes meaningful at high accumulation, you have direct evidence that full-gradient streaming is a bottleneck.
