## Why it works: COROSred is one model with two attention modes

From your code:
- [refiner.py:89](file:///Users/ivansamuel/Documents/Projects/telos/telos/diffusion/refiner.py#L89) runs the model with `mask_override=True`. That is causal (left-to-right) attention, which produces the draft and the confidence scores.

- [schedule.py](file:///Users/ivansamuel/Documents/Projects/telos/telos/training/schedule.py#L51-L174) blends three losses: α (next-token), β (fill in masked tokens) and γ (the confidence head). There is a floor that stops causal training from ever turning off (`alpha_min > 0`).

So COROSred needs only three things beyond a normal transformer:
1. a way to switch the attention mask
2. a `[MASK]` token
3. a small confidence head

Any pretrained decoder model (Qwen, Gemma, Granite, LFM) is already a transformer whose mask you can switch. It just hasn't learned the bidirectional mode yet.

## Evidence that converting existing models works
- **DiffuLLaMA** (Gong et al., *Scaling Diffusion Language Models via Adaptation from Autoregressive Models*, ICLR 2025) turned GPT-2 and LLaMA into diffusion models by gradually relaxing the causal mask during training.
- **Dream 7B** started from Qwen2.5 weights.

**Their weakness is your opening.** Those conversions give up the left-to-right mode: the result is a diffusion model only. COROSred keeps both modes and routes between them by confidence. That's the difference you'd claim.

## Conversion recipe
1. **Base model:** an open model with 1–4B parameters. AFM 3 itself is out: from what I found, Apple ships it only inside the OS, with no downloadable weights.
2. **`[MASK]` token:** reuse one of the tokenizer's unused reserved tokens, or add one and resize the embeddings.
3. **Confidence head:** a new linear layer on the final hidden states, starting from scratch.
4. **Continued training** with your existing α/β/γ schedule. Start α high so the model's left-to-right skill isn't damaged.

## The push: tie it back to Flash-MoE

Freeze the base model. Train the bidirectional mode only as LoRA adapters:

| Mode | Weights | Where |
|---|---|---|
| Draft (causal) | Base model, **completely unchanged** | RAM |
| Refine (bidirectional) | Base + LoRA experts, one per domain or span type | **Flash**, loaded on demand |
| Self-learning | Only the LoRA experts and the confidence head | Small writes, so the SSD wear problem goes away |

**Why this is strong:**
- **Draft quality can't get worse,** because the base model never changes. A reviewer can't argue that adding diffusion hurt the AR model.
- **The refiner becomes a Flash-MoE made of LoRA experts.** Each one is a few MB, so loading one from flash is cheap.
- **It feeds last turn's idea directly:** when the refiner fixes a token, train the RAM side to match, so flash reads per token should drop over time.
- **One conversion recipe works for any open model.** That's a "method" contribution, not "we trained one more small model."

Understood: you want a new model architecture, not a product. Here's one built around what device hardware is actually good and bad at.

## The starting point: device hardware economics

| Resource | On your Mac / phone | What it means |
|---|---|---|
| **FLOPs (compute)** | Mostly idle while generating one token at a time | **Effectively free** |
| **RAM bandwidth** | The real bottleneck. Tokens/s ≈ bandwidth ÷ bytes of active weights | **Expensive** |
| **Flash** | Huge (hundreds of GB), slow, fine at random reads | **Cheap capacity, high delay** |
| **Writing to flash** | Wears the drive | **Avoid for gradients, fine for small writes** |

Today's architectures are designed for datacenter GPUs. A device-native one should **spend FLOPs to save bytes, keep knowledge on flash, and never put flash delay on the critical path.**

## The architecture: Loop + Lookup + Refine

### 1. Core: one small block, run many times (FLOPs are free)
- A small block lives in RAM and runs N times per token. Read it once, compute many times.
- Run more loops on low-confidence tokens. COROSred's confidence head decides how many.
- Prior art: Universal Transformers, *Relaxed Recursive Transformers* (Bae et al., 2024), Huginn's recurrent depth (Geiping et al., 2025), *Mixture-of-Recursions* (2025). **Looping alone isn't new.**

### 2. Knowledge: big lookup tables on flash (the key trick)
- DeepSeek's **Engram** (verified just now) stores n-gram patterns in huge lookup tables. The table indices come from the input tokens, so they're **known before the forward pass**. That lets Engram prefetch from CPU DRAM with a reported throughput cost under 3%.
- **The device version:** put those tables on **flash** instead of DRAM. Compare with Flash-MoE (AFM 3 style):

| | Flash-MoE (AFM 3) | Flash lookup tables |
|---|---|---|
| Bytes read per token | Whole experts (MB) | A few table rows (KB) |
| When you know what to load | Mid-network, after the router decides | **Before the model even runs** |
| Flash delay | On the critical path | **Fully hidden by prefetching** |

That's a structural argument for why lookup tables suit flash better than experts do.

### 3. Output: COROSred draft-refine (more work per byte loaded)
- One refine pass covers many tokens with a single weight load, so it does more work per byte read than token-by-token generation. **Diffusion-style refinement suits bandwidth-limited devices.** Nobody seems to argue that angle.

### 4. Self-learning: write table rows, not gradients
- Learning a new fact or habit means **writing a few KB of table rows to flash**, not running gradient updates over the weights.
- That fixes the "training on flash destroys the SSD" problem we hit earlier. Learning becomes appending.
- Your personal knowledge lives in your rows. The core stays frozen and shared, so it can't collapse.

## The possible paper: the claim and the line

- **Claim:** *scaling laws measured in bytes moved per token,* not parameters or FLOPs. At equal bandwidth, Loop + Lookup + Refine should beat a dense or MoE model of equal speed on a device.
- **Where it gets stupid:** comparing at equal parameter count. A looped core *loses* that comparison, and reviewers will try it. **Only compare at equal bytes moved and equal delay.** That reframing is the contribution.
- **Honest novelty check:**
  - Each of the four parts exists somewhere.
  - New (to my knowledge, not yet searched): lookup tables on *flash* with hidden prefetch, writable rows as the learning mechanism, confidence controlling both loop depth and refinement, and the bytes-moved scaling framing.
  - **Engram is the closest prior work. Read it before anything else.**

## Weirder alternatives, in case this is too sane
- **Procedural weights:** store a tiny generator network that *computes* the weights on-chip every time instead of loading them. Ultimate "FLOPs for bytes." Probably sounds stupid at today's quality levels.
- **Merge the KV cache into the lookup tables:** long-context memory becomes rows on flash instead of a growing KV cache in RAM.

Want to stress-test Loop + Lookup + Refine (failure modes, what Engram already covers), or go weirder?

The short answer: **You cannot train on-chip, and you shouldn't try.** The standard, mathematically sound way to do this is **train off-chip (on MLX/CUDA), run on the liquid state silicon.**

Here is the concrete reasoning and hardware evidence.

---

### 1. Why On-Chip Training is Physically Impossible on 0.016 mm²

To train on-chip, you need synapses that change their weights. The simplest biological rule is **STDP** (Spike-Timing-Dependent Plasticity).

Let us check the silicon area of an STDP synapse on 180nm:
* **Weight storage (e.g. 6-bit counter / register):** ~6 D-flip-flops $\approx 180\ \mu\text{m}^2$.
* **Eligibility trace / timing counter:** Measure $\Delta t$ between pre- and post-spikes $\approx 150\ \mu\text{m}^2$.
* **Add/subtract & clamp update logic:** $\approx 120\ \mu\text{m}^2$.
* **Total area per plastic synapse:** $\approx 450\text{--}500\ \mu\text{m}^2$.

Your entire die is $0.016\ \text{mm}^2 = 16,000\ \mu\text{m}^2$.
* At $500\ \mu\text{m}^2$ per synapse, your entire chip budget is exhausted by **~30 synapses total**—with zero area left for neurons, routing, clock distribution, or I/O.
* A 30-synapse network cannot learn any non-trivial pattern.

---

### 2. How the MLX / CUDA + Silicon Reservoir Paradigm Works

The foundational principle of a **Liquid State Machine (LSM)** (Maass et al., 2002) is that **the reservoir itself is never trained**.

```
Input Signal (Audio/ECG/Sensors)
           │
           ▼
┌─────────────────────────────────┐
│     Silicon Chip (0.016 mm²)    │
│  Fixed Recurrent Spiking Die    │ ◄── 100% Fixed Metal Wires
│  Non-linear temporal projection │     Zero weight storage
└─────────────────────────────────┘
           │ Spike State Vectors
           ▼
┌─────────────────────────────────┐
│  Host (Mac via MLX / Python)    │
│    Trained Linear Readout       │ ◄── Ridge Regression / Linear SGD
│    W_out · State = Prediction   │     (Trains in <1 second)
└─────────────────────────────────┘
```

The split of responsibilities:

#### Phase A: Pre-Tapeout Optimization (on MLX / PyTorch)
1. **Model the reservoir digitally** (e.g. using `snnTorch` or a simple MLX recurrent LIF simulation).
2. **Topology Search:** Search for the recurrent connection graph (sparsity, balance of excitatory vs. inhibitory synapses, leak factor) that achieves the **"edge of chaos"** (spectral radius $\approx 1$, where the network exhibits high state separation and fading memory).
3. **Hardcode to Verilog:** Convert that exact wiring graph into fixed standard cells and synthesized metal wires.

#### Phase B: Inference & Readout Training (Post-Fabrication)
1. Stream time-series samples (e.g. spoken digits, heart ECG anomalies, IMU gestures) into the chip over SPI / GPIO pins.
2. The chip calculates the non-linear recurrent dynamics in real-time at micro-watt power.
3. Read out the reservoir's spike state vector $X \in \mathbb{R}^{T \times N}$ into your Mac.
4. Fit a closed-form linear readout on MLX:
   $$W_{\text{out}} = (X^T X + \lambda I)^{-1} X^T Y$$
   This solves in milliseconds and requires no backpropagation through time (BPTT).

---

### 3. What Does This Give You for a Paper?

This split makes the project realistic and publishable:

1. **Hardware novelty:** An ultra-compact ($0.016\ \text{mm}^2$) physical spiking reservoir on open-source silicon that does feature extraction with zero SRAM overhead.
2. **Host-accelerated readout:** The host (Apple Silicon / MLX) only evaluates a dot product ($W_{\text{out}} \cdot \mathbf{x}$), saving orders of magnitude of energy compared to running a full transformer or dense RNN on the host.

The good news is that **a buggy design cannot physically fry or break your tile.** 

Here is the exact hardware isolation architecture that prevents it:

---

### 1. You Don't Route Power (Zero Risk of VDD/GND Shorts)

On an ASIC, the only way to physically burn silicon is a dead short between power ($V_{\text{DD}}$) and ground ($V_{\text{SS}}$).

* Students do **not** draw metal wires or place raw power rails. You only submit HDL (Verilog).
* The synthesis toolchain (OpenLane / LibreLane) automatically generates standard CMOS gates and generates the Power Distribution Network (PDN).
* Before any design is accepted into the final wafer mask, GitHub Actions runs **DRC (Design Rule Checking)** and **LVS (Layout Versus Schematic)**. 
* If any tile had an internal short, the automated toolchain fails with an error and **refuses to include it on the tapeout**.

---

### 2. Output Muxing (No Bus Contention / Drive Fights)

Another classic way to burn hardware is bus contention—if Design A drives a pin to $3.3\ \text{V}$ (High) while Design B drives the same pin to $0\ \text{V}$ (Low), a high short-circuit current burns out the output pad drivers.

* In this architecture, **no student design connects directly to the physical package pins.**
* Instead, all 128 designs route into a central **Multiplexer Spine**.
* When you set the DIP switches to your design's ID, the mux connects **only your tile's 8 output lines** to the physical output pads. 
* All other 127 designs are disconnected from the external pins. Even if someone's code is outputting total garbage or rapid glitches, their signals stop at the mux.

```
Tile 001 (Buggy design)  ──────► [ MUX ]
Tile 002 (Someone's loop) ─────► [ MUX ] ──(DIP Switch selects Tile 042)──► Physical I/O Pins
Tile 042 (Your Neuromorphic) ──► [ MUX ] ─────────────────────────────────► (Your outputs only)
Tile 128 (Another design) ─────► [ MUX ]
```

---

### 3. Reset and Clock Isolation

What if someone built a runaway ring oscillator that draws massive current?
* The harness controls the clock and reset lines to every tile.
* Inactive tiles are held in **reset** or have their clocks gated so they sit dormant in static CMOS sleep mode (drawing mere nano-amps of leakage current).
* The GF180 power grid uses thick top-metal straps (Metal 4 & Metal 5) capable of delivering hundreds of milliamps—far more than a tiny $160 \times 100\ \mu\text{m}$ tile could ever draw.

Tiny Tapeout has run over **10 shuttle runs** (from TT01 through TT08+ on SkyWater 130 and GF180) with over 1,500 total community designs.
* Plenty of individual designs have had **logic bugs** (e.g. someone messed up a state machine and their own circuit didn't work).

### 1. What Are Spiking Neurons?

In standard AI (like GPT or Claude), every neuron outputs a continuous decimal number: `0.742`. To calculate an answer, billions of multiplications happen in lockstep.

A **Spiking Neuron** is modeled directly on biology. It **does not output numbers.** It only communicates through **discrete 1-bit pulses in time (spikes)**.

Think of it like a **leaky bucket**:

```
Input Spikes (drops of water)
       │       │
       ▼       ▼
   ┌───────────────┐
   │               │
   │  LEAKY BUCKET │ ◄── Leak: Water slowly drains out if nothing happens
   │  (Membrane V) │
   └───────┬───────┘
           │
      Is it full? (Threshold)
       /       \
     No         Yes
     │           │
     │           ▼
     │       FIRE SPIKE! (1-bit pulse)
     │       Reset bucket to empty.
     └───────────┘
```

1. **Integrate:** Every incoming pulse adds a little charge to an internal number called the **membrane potential**.
2. **Leak:** If no new spikes arrive, that charge gradually leaks back down to zero over time.
3. **Fire:** If several pulses arrive quickly, the charge hits a **threshold**, the neuron emits a single 1-bit pulse (`1`), and resets to zero.

Information is encoded in **when** the pulses arrive, not in large floating-point numbers.

---

### 2. Is It Like RISC-V, x86, or ARM?

**No. It is radically different.**

RISC-V, x86, and ARM are **von Neumann architectures**:
* They have a **CPU** and separate **RAM**.
* They fetch instructions one by one (`FETCH` $\rightarrow$ `DECODE` $\rightarrow$ `EXECUTE`).
* They constantly move data back and forth across a memory bus, which wastes 90% of a computer's power (the "von Neumann bottleneck").

A **Neuromorphic Spiking Chip is Non-von Neumann**:
* **No instructions:** There is no program counter, no assembly language, no `LOAD` or `STORE` instructions.
* **No separate memory:** The neuron's register **is** its memory and its compute all at once.
* **Massively parallel:** All neurons operate at the exact same time in parallel.
* **Event-driven:** When there are no incoming pulses, the circuit does **nothing** and draws virtually zero power. It only wakes up for the exact nanoseconds a pulse travels through it.

You aren't writing software for a processor; you are **building an artificial nervous system in silicon**.

---

### 3. What CAN We Actually Do With It?

Spiking neurons are terrible at static math (they cannot calculate $137 \times 492$). 

What they are extraordinary at is **real-time temporal pattern recognition at almost zero power**:

1. **Micro-Watt Audio Wake Words ("Hey Siri"):**
   * Normal CPUs must keep their microphone digitizer, memory, and core active just to listen for a word, draining battery.
   * A spiking chip sits idle consuming microwatts. When the specific temporal rhythm of your voice hits the reservoir, it fires an interrupt spike to wake up the main CPU.
2. **Event-Based Neuromorphic Vision:**
   * Used with DVS (Dynamic Vision Sensor) cameras on high-speed drones. Standard cameras take 60 frames per second. Neuromorphic cameras fire spikes whenever an individual pixel detects motion, allowing reaction times in microseconds.
3. **Biosignal Anomaly Detection (Wearables):**
   * Continuously monitoring a heartbeat (ECG) or brainwaves (EEG) inside a smartwatch or medical implant for months on a tiny coin-cell battery.

## 2. Core Architecture & Feature Specification

The chip offloads vector multiply-accumulate operations from 8-bit/32-bit microcontrollers that lack floating-point units (FPUs) or SIMD/DSP instructions.

### Supported Math Precision Modes:
1. **Mode 0: BitNet b1.58 Ternary Mode (Default):**
   * Weights are ternary: $W \in \{-1, 0, +1\}$, packed as 2 bits per weight (`2'b00` = 0, `2'b01` = +1, `2'b11` = -1).

   * Math: Multiplier-free! Multiplexers select $+A$, $-A$ (two's complement), or $0$.

2. **Mode 1: 1-Bit Binary Neural Network (BNN Mode):**
   * Weights and Activations are binary bits ($1 \in \{+1\}$, $0 \in \{-1\}$).
   * Math: 32 parallel XNOR gates + popcount adder tree.
3. **On-Chip Features:**
   * **24-Bit Saturation Accumulator:** Holds running sums across multiple 32-element chunks without overflow.
