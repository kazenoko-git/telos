# Télos v1.8.2 validation

Physical accelerator results supplied on 2026-11-19 cover the v1.8.2 tag,
commit `e0b368ae720cf2f81c1d2a24b689aeead4ce8d87`. These are short
correctness and replay checks on synthetic token data, not sustained performance,
model-quality, or general backend acceptance results. The local release suite
passed **464 tests, with 7 skipped**, before the tag was pushed.

## Actual AR trainer: representative model

Both hardware checks used `UnifiedPyTorchTrainer`, native AdamW, and a
49,166,848-parameter causal Transformer: width 512, 14 layers, 8 attention and
KV heads, tied embeddings, vocabulary 8192, sequence length 256, and dropout 0.
Gradient checkpointing and `torch.compile` were disabled. Training used 16
update steps, 8 warmup steps, LR cadence 1, and a memmapped synthetic token file.
Each replay stopped after saving step 8 in a separate process and resumed through
step 16 in a fresh process.

| Check | Single TPU v5e-1 runtime | Kaggle 2 × Tesla T4 |
| --- | --- | --- |
| Framework | Torch 2.9.0+cpu / Torch-XLA 2.9.0; physical execution on `xla:0` | Torch 2.11.0+cu130; CUDA 13.0; driver 580.178.04 |
| Precision | BF16 requested; observed BF16 Q/output projection tensors; parameters FP32 | BF16 requested; native-support guard selected FP16; observed FP16 Q/output projections; parameters FP32 |
| Scaling | No CUDA GradScaler | GradScaler enabled on both ranks; scale 65,536; no overflow-skipped updates |
| Accumulation | Microbatch 8 × 4; effective batch 32 | Per-rank microbatch 8 × 4; global effective batch 64 |
| Execution count | 64 forwards / 16 optimizer updates | 64 forwards / 16 actual optimizer updates on each rank |
| Gradient clipping | Norm limit 1.0 | Disabled with `grad_clip=0.0` |
| Gradients reaching optimizer | Finite, nonzero throughout | Finite, nonzero throughout; rank gradient norms matched |
| Recorded peak device allocation | 2,101,395,968 bytes, about 2.10 GB | 2,150,938,112 bytes per GPU, about 2.15 GB allocated; 2,220,883,968 bytes reserved |
| Resume comparison | Notebook reports exact equality for all listed checkpoint fields | Notebook reports exact equality on both ranks for all listed checkpoint fields |

The TPU comparison covered model, optimizer, scheduler, Python/NumPy host RNG,
Torch RNG, XLA RNG, data cursor, global step, precision, master-parameter field,
and scaler field. Resumed gradient norms match uninterrupted steps 9–16.
See [TPU summary](../../reports/releases/v1.8.2/tpu_full_trainer/summary.json),
[reference report](../../reports/releases/v1.8.2/tpu_full_trainer/reference.json),
and [resumed report](../../reports/releases/v1.8.2/tpu_full_trainer/resumed.json).

CUDA comparison additionally covered GradScaler state, CUDA RNG, rank, world
size, and visible CUDA device count. DDP replicas had identical model, optimizer,
and scaler hashes in the notebook comparison. Distinct first-row markers were
observed on ranks 0 and 1, both initially and after resume. This validates the
checked starting data slices and resumed cursor, not every possible dataset or
wraparound case. See [CUDA summary](../../reports/releases/v1.8.2/cuda_ddp/summary.json)
and [rank 0](../../reports/releases/v1.8.2/cuda_ddp/reference.rank0.json) /
[rank 1](../../reports/releases/v1.8.2/cuda_ddp/reference.rank1.json) reports.

No tolerance was relaxed for the exact checkpoint comparisons. The CUDA workers
requested deterministic algorithms and set `CUBLAS_WORKSPACE_CONFIG=:4096:8`.
Exact replay is established for that configuration, not arbitrary CUDA kernels
or nondeterministic execution. No overflow occurred, so GradScaler overflow
recovery was not exercised. The CUDA check establishes that `grad_clip=0` permits
nonzero updates; it is not a separate comparison against a no-clipping reference.

## TPU compilation and optional optimizer

A separate isolated optimizer check ran 32 updates on the physical TPU. The
candidate matched the CPU reference within the existing tolerances, with maximum
parameter difference **2.384185791015625e-7** and identical host learning rates.
Compilation count reached two after the second update and stayed there.
See [optimizer check](../../reports/releases/v1.8.2/tpu_optimizer/optimizer_validation.json).

A small FP32 AR comparison (width 128, two layers, vocabulary 128, batch 4,
sequence 64, dropout 0) tested native AdamW and the optional `XLAAdamW`. Both
stabilized after two compilations in their first trials. Later trials reused
cached graphs. Native/candidate state comparisons passed numerical tolerances;
four-update gradient comparisons passed; candidate checkpoint/resume matched
exactly. Each measured ABBA trial lasted less than 0.6 seconds, so the roughly
2.1% pooled difference does not establish a sustained speed advantage.
See [comparison report](../../reports/releases/v1.8.2/tpu_optimizer/training_comparison.json).

The representative BF16 native-trainer run recorded **five compilation events**
across 16 updates, including diagnostic/checkpoint work. It does not support the
audit's claim of one recompilation per changing warmup LR on this stack. The
archived full-trainer metrics do not locate each compile by step.

Keep native AdamW as the default. The optional optimizer was not tested through
the representative BF16 full-trainer configuration. These results do not show
that a custom optimizer was necessary to solve LR-driven recompilation.

## Performance limits and remaining scope

Full-trainer wall times include initialization, compilation, diagnostic hooks,
logging, and checkpoint I/O. They do not measure steady-state throughput or
DDP scaling efficiency. Memory figures are framework-reported allocations, not
whole-machine memory requirements. No cross-backend numerical equivalence is
claimed: the TPU and CUDA runs used different precisions and effective batches.

These hardware runs do not establish long-run stability, model quality, other
model shapes, nonzero dropout replay, TPU multi-chip behavior, native CUDA BF16,
negative clipping thresholds, positive CUDA clipping behavior, compile-enabled
training, activation checkpointing, diffusion/COROSred, post-training, or GRPO.
The disabled-clipping and BF16 safeguards have additional local regression
coverage, but that does not expand the physical-hardware claims above.

## Evidence provenance and reproduction

[Archived JSON reports and logs](../../reports/releases/v1.8.2/README.md) were
copied from the three user-supplied result ZIPs. The manifest records original
archive hashes and hashes of every retained file. Large `.pt` checkpoints were
excluded. Consequently, exact equality is recorded from the notebook's comparison
summaries; it cannot be independently recomputed from the archived logs alone.
The full-trainer notebook harnesses are not included in those ZIPs. Their
configurations, per-phase assertions/results, framework details where captured,
and execution logs are retained.

The isolated TPU commands in the release remain reproducible with:

```sh
TORCH_DEVICE_BACKEND_AUTOLOAD=0 PJRT_DEVICE=TPU \
  python scripts/validate_xla_dynamic_optimizer.py --device xla --steps 32 \
  --output optimizer_validation.json
TORCH_DEVICE_BACKEND_AUTOLOAD=0 PJRT_DEVICE=TPU \
  python scripts/compare_tpu_optimizers.py --device xla \
  --output training_comparison.json
```

The supplied Python 3.13 TPU environment used Torch 2.9.0, Torch-XLA 2.9.0,
and libtpu 0.0.21.1 after the pinned TPU extra failed to install libtpu 0.0.21.
`TORCH_DEVICE_BACKEND_AUTOLOAD=0` avoided loading an incompatible preinstalled
`torch_tpu` plugin. Package installation details are conversation provenance;
libtpu's version is not independently recorded in the hardware JSON.
