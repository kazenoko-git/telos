# Native inference validation for v1.9.0

The initial inference workflow loads a native causal checkpoint and its tokenizer, then generates or streams a raw-text continuation. PyTorch uses reserved KV storage by default. MLX uses an incremental dynamic cache. Both project only the position used to select the next token.

## Checkpoint workflows

On an Apple M5 Pro, separate CLI processes ran AR pretraining, one SFT run, and generation on each of PyTorch CPU and MLX Metal. The training corpus repeated `hello world again`, using a custom eight-token tokenizer and a 16-token context. Both pretraining exports generated `world again hello world again hello` from `hello` with a six-token limit. Both SFT exports generated `world again`.

The SFT output directories were copied to new locations and the source tokenizer file was moved before generation. Both relocated exports loaded their packaged tokenizer. Cached and uncached continuations matched. These are checkpoint interoperability checks on a toy corpus.

The inference tests also cover reserved-cache storage identity and logit parity, greedy token parity with full-prefix recomputation, seed reproducibility, custom tokenizer resolution, EOS, overlapping stop strings, context limits, and streaming UTF-8 across token boundaries.

## Decode throughput

Local M5 Pro measurements used 49M randomly initialized models, PyTorch FP32 on CPU with six threads, and MLX 0.32.2 BF16 on Metal. Each prompt was a fixed random token sequence. Every path generated 48 greedy tokens and produced the same IDs as its backend's uncached path. Tokens were counted directly to keep EOS and text rendering out of the timing. Each mode had one four-token warmup, followed by six measured generations in forward and reverse mode order.

| Backend | Prompt tokens | Uncached tok/s | Dynamic KV tok/s | Reserved KV tok/s |
| --- | ---: | ---: | ---: | ---: |
| PyTorch CPU | 128 | 43 | 316 | 382 |
| PyTorch CPU | 512 | 17 | 234 | 299 |
| MLX Metal | 128 | 410 | 860 | — |
| MLX Metal | 512 | 205 | 690 | — |

Rates are medians for the 47 tokens generated after the first token. At 512 prompt tokens, median time to the first token was 60.8 ms on the reserved PyTorch path and 3.4 ms on the cached MLX path. Peak MLX allocation fell from 272 MiB uncached to 246 MiB cached for that shape. PyTorch peak memory was not measured.

These measurements isolate decode rather than checkpoint loading, tokenization, or CLI startup. The reserved cache allocates space for the prompt and the bounded continuation when decoding continues past the first token. CUDA support still needs physical validation. The measurements do not establish throughput or parity on CUDA.

## Native Qwen3 (Bonsai 4B 2-bit) and LM Studio comparison

On the M5 Pro with MLX 0.32.2 and the original Ternary Bonsai 4B 2-bit Safetensors checkpoint (212 prompt tokens, 1,024 context, 192-token greedy budget, four alternating fresh loads per runtime), native Telos in-process generation recorded **113.5 ms** median TTFT, **145.19 tok/s** decode across the shared 191-token window, and **1.427 s** wall time (1,607 MiB MLX allocator peak), compared to LM Studio SDK 1.5.0 at **197.7 ms** TTFT, **124.33 tok/s** decode, and **1.723 s** wall time (+1,868 MiB process-tree RSS delta), with exact 813-character output parity after LM Studio's leading-space trim. Final-position prefill subsequently reduced median first-token latency by **2.5%** (212 prompt tokens) and **1.7%** (848 prompt tokens). See `reports/bonsai4b_kv_cache_2026-11-24/RERUN.md` and `reports/bonsai4b_prefill_2026-11-25/README.md`.

## Generation endpoint (`telos serve`), prefix KV reuse, and additional MLX architectures

- **OpenAI-compatible endpoint**: `telos serve` (optional `telos-ml[serve]` extra) serves `/health`, `/v1/models`, `/v1/completions`, and `/v1/chat/completions` with SSE streaming, sandboxed Jinja2 chat templates (plus role-prefix fallback), Bearer auth, and `X-Telos-TTFT-Ms`, `X-Telos-Decode-Tok-Per-Sec`, and `X-Telos-Cached-Tokens` headers. Verified on CPU with `tests/test_serve.py` and `tests/test_lmstudio_endpoint_parity.py` (including `OpenAIAPIAdapter` interoperability).
- **Exact prefix KV reuse**: Multi-token cached suffix prefill and bounded LRU `PrefixKVCache` (`--prefix-cache-entries`) reduced PyTorch CPU median TTFT on an 8-layer `d_model=512` model with `240/256` shared prefix tokens from **21.79 ms** to **5.67 ms** (**3.85×** speedup) with exact output parity.
- **Additional native MLX architectures & pipelined sampling**: Added `LlamaMLX` (`llama`/`mistral` with Llama 3 smooth RoPE scaling), `Qwen2MLX` (`qwen2`), and `Phi3MLX` (`phi3`), plus 1-step device-resident pipelining for sampled cached MLX decode (`_mlx_pipelined_cached_tokens`).
- **Saved HTTP/SSE comparison**: The [2026-11-25 report](../../reports/serve_vs_lmstudio_2026-11-25.json) records four trials per workload at a 192-token cap. Short greedy generation measured median TTFT of 19.67 ms for Telos and 101.11 ms for LM Studio, with 136.90 and 128.20 decode tok/s respectively. All three greedy workloads reported different text between runtimes. The seeded sampled workload records timings without a parity result. This artifact does not establish exact endpoint output parity or explain the differences.

## Routing training implemented in v1.9.0

Window distillation trains low-rank selector and token-routing deltas, a selector bias, and selected LoRA projections. The PyTorch wrapper freezes the original gate. The native MLX post-training path freezes the base through LoRA attachment before adding trainable routing adapters, and rejects full fine-tuning for external MLX checkpoints. Adapter exports retain the routing delta tensors.

**Full-router training has not been implemented for Inkling 2 Mini, Qwen 3.5 MoE, or Gemma 4 26B A4B.** Existing adapter distillation results do not establish the quality or speed of that proposed training mode. [PyTorch routing implementation](../../telos/training/inkling2_window_distill.py) · [MLX post-training](../../telos/posttrain/trainer.py) · [MLX routing adapters](../../telos/models/window_routing.py)


## Post-release full-router implementation

The current checkout adds opt-in `router_training="full"` to `posttrain` and the PyTorch window-distillation patchers, plus `--router-training full` to the CLI. It requires distillation with a positive window size. The default remains `adapter`. This addition follows the v1.9.0 release described above.

Full mode learns an unconstrained FP32 matrix for the window selector and a second for token routing. Each matrix is a zero-initialized update added to the frozen base projection. Selector bias remains trainable, and the existing selected LoRA projections train alongside the routing matrices. Router normalization/scaling parameters and expert weights remain frozen. Teacher evaluation uses the frozen base router. The learned matrices have no low-rank constraint and are stored as `selector_weight` and `token_weight` in the existing adapter format. Export metadata records the chosen mode.

Tiny CPU fixtures cover Inkling's repeated layer visits, Qwen 3.5 shared experts and mixed attention layout, and Gemma 4 router normalization/per-expert scaling. They check routing gradients and export/reload. Tiny native MLX tests exercise post-training and reload for all three architectures, and Inkling also checks checkpoint resume. These tests establish fixture behavior. At the initial fixture stage, real-model quality, optimizer memory, throughput, CUDA execution, and TPU execution were unverified for full-router mode.

For the first real training experiment, the existing Modal H100 runner accepts `router_training="full"` and its local entry point accepts `--router-training full`. The same runner accepts a model ID for each supported architecture. This change did not launch a Modal job. The public window-distillation API currently accepts MLX, CUDA, and CPU backends. TPU/XLA would require further integration and verification.

Post-release local verification on 2026-11-27 passed 40 routing/distillation tests across the five targeted test files. Adding the Inkling inference file yielded 61 passed and one failure in `test_fast_uint2_nvfp4_kernels_match_reference`. That same test failed in an isolated extraction of the pre-change commit `af1d0236`, confirming an existing fast-kernel parity issue. The full-router feature does not depend on enabling that optional fast kernel.


## Subsequent H100 pilot validation

Published telos-ml==1.9.1rc2 completed eight-step full-router pilots on the real Inkling 2 Mini, Qwen 3.5 MoE, and Gemma 4 26B A4B checkpoints. Each model had finite, nonzero first-step gradients in every selector and token-routing matrix, active coverage supervision, and exact parameter and held-out logit parity after export/reload. Held-out response NLL improved on eight prompts per model. Peak allocated GPU memory was 50.90, 67.22, and 49.57 GiB respectively.

The initial hosts were overallocated at four CPU cores and 128 GiB RAM. Gemma completed after reducing the host to two vCPU and 8 GiB RAM. The runner retains the reduced limits for future work. TPU execution and longer-run generalization remain unverified. [Raw metrics, resource correction, artifacts, and cost estimates](../../reports/full_router_h100_2026-11-27/README.md)
